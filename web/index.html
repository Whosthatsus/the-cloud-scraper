Architectural Philosophy

The Architecture of Web Intelligence

Modern web data extraction often struggles with brittle infrastructure, uncontrolled execution loops, and unverified network exposure. The Cloud Scraper addresses these challenges through a strict, least-privilege serverless state machine.

Every execution is decoupled: Amazon API Gateway accepts extraction triggers asynchronously with HTTP 202, AWS Step Functions coordinates autonomous Lambda workers, and unexpected target barriers are isolated into an Amazon SQS Dead-Letter Queue without stalling upstream data consumers.

Orchestration State Machine

AWS Step Functions Flow

The pipeline implements a decoupled, standard state machine orchestrating 5 dedicated Lambda tasks with an isolated SQS Dead-Letter Queue.

[REST API Gateway / EventBridge Schedule]
  ↓ POST /scrape
[Job Dispatcher Lambda] → start_execution()
  ↓
[AWS Step Functions: the-cloud-scraper-pipeline-sm]
  ├−− Task 1: Scraper Lambda (SSRF safe, robots.txt, S3 raw HTML archive)
  ├−− Task 2: Validation Lambda (Schema validation & required field check)
  ├−− Task 3: Transformation Lambda (Mojibake repair & SHA-256 fingerprint)
  ├−− Task 4: Storage Lambda (Amazon DynamoDB & S3 JSON data lake)
  ├−− Task 5: Notification Lambda (FinOps cost calculation & SNS alert)
  └−− Catch [States.ALL] → Route Failure to SQS DLQ → SNS Alert → Fail
Dual-Tier Storage

S3 Data Lake vs DynamoDB

Tier 1 — S3 Data Lake: Partitioned raw HTML snapshots stored under raw/{site_id}/{timestamp}/page.html for auditability and compliance.

Tier 2 — DynamoDB NoSQL: Clean, deduplicated entity records indexed with composite partition key site_id and sort key record_id (SHA-256 hash).

Network Security

SSRF & Redirect Defense

Every outbound connection validates IP literals and resolved hostnames against RFC 1918 private networks, link-local addresses (169.254.0.0/16), and IPv6 loopbacks. Redirect hops are bounded and individually re-evaluated.
